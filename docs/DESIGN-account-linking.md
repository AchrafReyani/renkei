# Design: account linking (v0.2)

Status: **draft / awaiting decision.** This proposes how renkei should
implement LINE account linking. It does not change code yet.

renkei-core already parses and verifies the `accountLink` webhook
(`LineAccountLinkEvent { link: { result, nonce } }`, `isAccountLinkEvent`),
and `POST /line/webhook` receives the event but currently only logs it. This
doc decides what happens next: **how the LINE-issued link maps to a downstream
account.**

## What LINE account linking actually is

LINE's flow (Messaging API "Linking user accounts") has four steps:

1. **Mint a link token.** `POST https://api.line.me/v2/bot/user/{userId}/linkToken`
   with the **Messaging API channel access token** returns a one-time
   `linkToken` (~10 min TTL). This requires already knowing the LINE
   `userId` — so linking can only start from a context where the user is
   identified: right after a renkei LINE login, inside LIFF, or from a chat
   with the OA.
2. **Redirect** the user to
   `https://access.line.me/dialog/bot/accountLink?linkToken={linkToken}&nonce={nonce}`.
   The **nonce** is generated by *us* (renkei or the app), stored server-side
   against the account we intend to link, one-time, ≥10 chars, cryptographically
   random.
3. **User consents** in the LINE app.
4. **`accountLink` webhook** arrives at the Messaging API webhook endpoint:
   `{ type: 'accountLink', source: { userId }, link: { result: 'ok' | 'failed', nonce } }`.
   On `ok`, we resolve `nonce → account` and persist `userId ↔ account`.

Two things renkei does not have yet, needed for step 1: the **Messaging API
channel access token** (distinct from the channel *secret* it already holds for
webhook signature verification), and a **nonce store** (renkei already has
`storage.payloads` with TTLs — the login flow uses it — so this is mostly reuse).

## The real decision

renkei already knows the LINE `userId` from Login (it *is* the `sub`, stable
per provider). So the question is not "how do we get the userId" — it is
**what account does the nonce bind to, and who owns that mapping.** That splits
into two options that actually serve two different use cases.

### Option A — renkei-owned link, exposed as a claim (recommended first)

renkei owns the whole flow. `/link/start` is hit by a user who already has a
renkei login (so `sub` is known); renkei mints the linkToken, stores
`nonce → sub`, and redirects to the accountLink dialog. The `accountLink`
webhook resolves `nonce → sub` and records the link in renkei's own storage.
Downstream apps **read the result as an OIDC claim** (e.g. `line:linked: true`)
— exactly how the job platform consumed `line:friend`: zero webhook code in the
app.

- **Binds:** a LINE identity ⇄ its own renkei `sub` (confirming the OA↔account
  consent, and enabling later cross-region / cross-provider linking under the
  same identity).
- **Fits:** apps whose users are keyed by the renkei `sub` — i.e. "sign in with
  LINE" apps, including the current job-platform dogfood.
- **Pro:** matches renkei's value prop (broker owns the mapping, app just reads
  claims); centralizes linkToken minting + webhook verification; smallest app
  surface.
- **Con:** renkei must hold the Messaging API channel access token; it does not,
  by itself, solve "link LINE to a *pre-existing* email/password account" (see B).

### Option B — forwarded link, app-owned mapping

The **downstream app** owns the nonce and the binding, tied to *its* logged-in
user — which may be a non-LINE (email/password) account. renkei's role shrinks
to two services: optionally **proxy the linkToken mint** (since it holds the
channel access token), and **verify + forward** the `accountLink` webhook as a
trusted `{ userId, nonce, result }` POST to a configured app callback, so the
app never has to expose its own Messaging API webhook or implement HMAC
verification. The app matches `nonce → its user` and writes
`appUser ⇄ lineUserId` in its own DB.

- **Binds:** a LINE identity ⇄ an arbitrary downstream account renkei has no
  concept of.
- **Fits:** the "Connect LINE" button in the settings of an existing
  password account — only the app (where the user is authenticated with their
  password) can assert that the email account and the LINE identity are the
  same person; renkei cannot.
- **Pro:** renkei stays a thin broker with no opinion on "account" semantics;
  the app keeps full ownership.
- **Con:** more moving parts (app needs a relay endpoint + nonce store); the
  link is not automatically an OIDC claim; renkei and the app must agree on
  nonce format and callback auth (shared secret / signature).

### They are not either/or

A and B serve different users. A user who *only* logs in with LINE is
Option-A-shaped (their account *is* the `sub`). A user with a pre-existing
password account "connecting LINE" is Option-B-shaped (a merge only the app can
authorize). The current job-platform dogfood creates the account *from* LINE,
so it is Option-A-shaped today.

## Recommendation

**Build Option A first**, as a v0.2 slice, and document Option B as the
follow-up for the "link to an existing app account" case. Reasons: it fits
renkei's model and the dogfood, reuses the claim-consumption pattern the app
already has, and the linkToken/nonce/webhook plumbing it builds is exactly what
Option B later reuses. The objection worth stating: the *long-term* dogfood
(a job-seeker who signed up with email later adding LINE) wants B — but that is
not the flow the app has today, and A is the prerequisite for B regardless.

## Concrete surface if we take Option A

- **Config:** add `messagingChannels[].channelAccessToken` (needed to mint the
  linkToken). Open question: long-lived vs. short-lived-with-refresh token.
- **Storage:** nonce store via existing `storage.payloads`
  (`upsert('renkei:link', nonce, { sub }, ttl)`); a persisted link record on the
  identity (e.g. `linkedAt`), so the claim survives restarts.
- **Routes:** `GET /link/start` (requires an active renkei login; mints
  linkToken, stores nonce, redirects to the accountLink dialog); handle
  `accountLink` inside the existing `POST /line/webhook` (resolve nonce → sub,
  set the link, drop the nonce; `result: 'failed'` → clear the nonce and no-op).
- **Claim:** extend `buildClaims` with `line:linked` (boolean) and/or
  `line:linked_at`.
- **core:** a `startAccountLink()` helper (mint linkToken + build the dialog
  URL) mirroring the existing `buildAuthorizeUrl()` shape, unit-tested with an
  injected `fetch`.

## Open sub-decisions for Achraf

1. **A first, B later?** (recommended) — or is the "connect LINE to an existing
   password account" case (B) needed soon enough to shape the API now?
2. **linkToken access token:** where it lives in config, and whether renkei
   mints it or (for B) proxies the mint for the app.
3. **What downstream sees:** a boolean `line:linked` claim (simplest) vs. a
   richer linked-identity claim.
4. **`/link/start` entry:** require a live renkei login session, or accept a
   one-time ticket the downstream hands over (needed for B).
